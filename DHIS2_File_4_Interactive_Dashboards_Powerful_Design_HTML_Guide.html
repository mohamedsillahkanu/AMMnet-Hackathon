DHIS2 Interactive Dashboards

Step-by-Step Guide to Building Powerful, Interactive and Professional Programme Dashboards

Purpose: This guide moves beyond simply adding charts to a dashboard. It explains how to design a dashboard as a decision-support product: define the questions, prepare indicators, create visualizations, arrange the page, add filters and interactions, test performance, and publish it for the intended users. Insert screenshots from your own DHIS2 instance at every marked location.
Step 1: Define the Dashboard Purpose

Start with the decision the dashboard is intended to support. Do not begin by adding charts.

Example: NMCP Malaria Situation Dashboard

Primary questions:
• What is the current malaria burden?
• Where is malaria burden highest?
• Is performance improving or declining?
• Which interventions have coverage gaps?
• Where are data-quality problems occurring?
Expected result: You have a short list of decisions/questions that determines what belongs on the dashboard.

Step 8: Create a Trend Chart

Use a line chart when the primary question is how an indicator changes over time.

Action: Open Data Visualizer → Select the indicator → Select Period → Select Organisation Unit → Choose Line Chart → Save.
Example: Confirmed malaria cases by month, January 2025–December 2026.
Expected result: The chart shows the temporal pattern and makes increases, decreases and seasonal peaks easier to identify.

Step 9: Create a District Comparison Chart

Use a bar/column chart when comparing multiple districts for the same indicator and period.

Action: Select the indicator → Select districts/organisation units → Select period → Choose Bar/Column Chart → Save.
Example: Malaria incidence by district for the selected year.

Step 10: Create an Interactive Map

Use maps when geographic variation is important.

Action: Open Maps → Select the indicator → Select the organisation-unit level → Configure the map → Save.

Choose the organisation-unit level that matches the analytical question, such as district or chiefdom.

Expected result: The map communicates geographic variation without requiring users to read a large table.

Example categories:
<25 | 25–50 | 50–75 | >75

Step 23: Avoid Dashboard Overload

Do not place every available indicator on one page.

  • Remove duplicate charts.
  • Combine related information where appropriate.
  • Move detailed tables below headline information.
  • Use separate dashboards or sections for different programme questions.
  • Keep the first screen focused on the most important information.
Expected result: A user can identify the main situation quickly and then explore details as needed.

Step 27: Test Data Accuracy

Compare dashboard values against known source values.

Example:
Source data: 220 tests, 150 positive
Dashboard positivity: 150 ÷ 220 × 100 = 68.2%

Check at national, district and facility levels as appropriate.

Expected result: Dashboard figures agree with validated source/analytics results.

Step 28: Test Performance

Large dashboards can become slow when they contain many complex visualizations.

  • Remove unnecessary visualizations.
  • Avoid excessive numbers of maps on one page.
  • Use appropriate periods and organisation-unit levels.
  • Test dashboard loading time with realistic user permissions.
  • Test during normal system load.

Step 30: Final Dashboard Approval

Before deployment, perform a formal review of the dashboard.

  • ☐ Purpose is clearly defined.
  • ☐ Indicators use approved programme definitions.
  • ☐ KPI cards are meaningful.
  • ☐ Trends use appropriate time periods.
  • ☐ Maps use appropriate organisation-unit levels.
  • ☐ Tables provide necessary detail.
  • ☐ Filters work correctly.
  • ☐ Organisation-unit access is correct.
  • ☐ Data-quality information is included where needed.
  • ☐ Dashboard values have been verified.
  • ☐ Dashboard performance is acceptable.
  • ☐ Sharing/access is correct.
  • ☐ Users have tested the dashboard.
Final result: The dashboard is ready for user acceptance and controlled programme deployment.

Powerful dashboard design principle: The strongest DHIS2 dashboard is not the one with the most charts. It is the one that lets a programme manager move quickly from “What is happening?” → “Where is it happening?” → “Why might it be happening?” → “Where should I investigate?”, while keeping the underlying definitions and data quality visible.
